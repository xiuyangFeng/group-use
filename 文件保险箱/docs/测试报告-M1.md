## 3. 断电注入（最关键的安全性验证）

### 3.1 方法

- 在代码关键步骤埋点，环境变量 `FDVAULT_CRASH_AT="步骤名=第几次"` 命中时直接 `os._exit(70)`，
  模拟"写入过程中拔电源/强杀进程"。
- 恢复逻辑**不依赖日志**，以 `manifest.db` + 文件系统实际状态为准，逐条把文件带到目标状态，
  可重复执行（幂等）。**正常操作与恢复共用同一套 `_finalize_lock` / `_finalize_unlock` 代码**，
  日常路径本身就是恢复路径。
- 每次恢复后比对整棵明文树：**每个文件 SHA256 + mtime（纳秒）+ 权限位 + 目录结构**，任一不同即失败。

### 3.2 全覆盖矩阵（21 个 pytest case，全部通过）

| 阶段 | 注入点（每个都单独测过） | 结果 |
|---|---|---|
| 解锁 | 密文校验后 / rename 前 / rename 后 / manifest 提交前 / 提交后 / 删 blob 前 / 删 blob 后 | ✅ 7/7 恢复后数据完全一致 |
| 解锁 | 第 2、4 个文件时崩溃（验证批量边界） | ✅ 2/2 |
| 解锁 | 崩溃后选择**回滚**（回到已上锁） | ✅ 回滚成功、回滚后仍能正常解锁 |
| 上锁 | 写 blob 前 / rename 后 / manifest 提交前 / 提交后 / 删明文前 / 删明文后 | ✅ 6/6 恢复后数据完全一致 |
| 上锁 | 第 2、4 个文件时崩溃 | ✅ 2/2 |
| 上锁 | 崩溃后选择**回滚**（回到已解锁） | ✅ 回滚后明文完整 |
| 恢复 | **恢复过程中再次断电**，然后再恢复 | ✅ 数据完整 |
| 恢复 | 恢复时输错密码 | ✅ 拒绝且不改动任何文件，状态保持"待恢复" |

## 4. 性能（实测）

测试命令：

```bash
.venv/bin/python scripts/bench.py --files 10000 --file-size 1000000 \
    --report reports/bench-10k-10gb.json
```

| 场景 | 创建（含首次上锁） | 解锁 | 上锁 | 校验 |
|---|---|---|---|---|
| **1 万文件 × 1 MB = 9.3 GB** | 41.4 s | **49.1 s** | **42.8 s** | 25.4 s |
| 最终代码复跑（含文件占用预检，2026-11-01） | 43.7 s | **44.3 s** | **53.3 s** | 22.4 s |
| 1 万文件 × 200 KB = 1.9 GB | 11.7 s | 14.6 s | 12.9 s | 8.5 s |

- 吞吐量约 **200–233 MB/s**；瓶颈是每个文件的 fsync + SQLite 提交，不是加密 CPU。
- 验收目标"10 GB / 1 万文件上锁+解锁各 5 分钟内"：**达标（43–49 秒）**。
- 说明：原地解锁会删除密文，所以每次上锁都是全量重新加密，**上锁与解锁耗时接近**——
  这是"磁盘只剩 10%、不能同时留明文+密文两份"的必然代价，已在需求和方案中确认。
- 解锁长这样：约 1 万文件 9 GB → 一杯咖啡没喝完就好了。

原始数据：[`reports/bench-10k-10gb.json`](../reports/bench-10k-10gb.json)、
[`reports/bench-10k-2gb.json`](../reports/bench-10k-2gb.json)

> 未做的性能项：10 万文件 / 100 GB 外接盘（M4 用真实试点数据量补测）。

## 5. 安全性质检查

| 性质 | 验证方式 | 结果 |
|---|---|---|
| 上锁后不残留明文 | 逐字节扫描 `.vault`（manifest、journal、header、blob），找明文文件名和内容串 | ✅ 通过 |
| 文件名保密 | manifest 里路径用 AEAD 加密，明文名不落盘 | ✅ 通过 |
| 密文被改/截断/换块/换文件 | 篡改测试 + 每块 AEAD 的 AAD 绑定文件 uuid、块号、是否末块 | ✅ 全部被发现 |
| 错误密码 | 拒绝解锁，状态不变，审计记 `UNLOCK_FAILED` | ✅ 通过 |
| 恢复密钥 | 32 字符 Base32，容错输入；错误密钥拒绝；重置密码后旧密码失效 | ✅ 通过 |
| 审计日志 | SHA-256 哈希链；改记录/删行可发现；导出 CSV 写明"半弱审计"局限 | ✅ 通过 |
| 两个窗口同时操作 | 文件锁（flock），第二个进程被拒绝并提示 | ✅ 通过 |
| manifest 丢失 | 解锁/校验拒绝并提示从备份恢复（不会"静默解锁成空文件夹"） | ✅ 通过 |

1. `journal.jsonl` 曾记录明文文件路径 → 上锁后 metadata 泄漏文件名。已改为只记 uuid，并加测试扫描。
2. 压力测试脚本自身判定逻辑写错（把"上锁后明文树为空"当成数据丢失）→ 已修正。

## 6. 已知限制（M1 范围，不含 M2–M4 功能）

1. **没有界面**：只有命令行，无托盘、无自动上锁、无右键菜单 → M2/M4。
2. **没有 Windows 实测** → M3。
3. **安装包未签名**：Windows 会弹"仍要运行"、macOS 要右键打开 → M3 写进安装说明。
4. **单文件上限按 < 1 GB 设计**，未测 4 GB 单文件；空间检查按 `2 × 最大文件 + 32 MB` 保守估计。
5. **未模拟"操作中途磁盘写满（ENOSPC）"**；开始前会检查并拒绝，但中途写满的表现 M2 再做。
6. **NFC/NFD、Windows 保留名、超长路径未测** → M3 专项。
7. 解锁期间明文对同机其它进程可见（Spotlight、缩略图、云同步）；这是"原地解锁"方案固有风险，
   靠独立系统账户 + 用完即锁 + 磁盘加密缓解，已在需求文档写明。
8. 崩溃恢复需要再输一次密码；恢复过程可被再次中断（已测）。
9. **审计是半弱审计**：密码共用 + 本机管理员可改日志，只能证明"谁在操作"。

## 7. 复现方式

```bash
cd 文件保险箱
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt -r requirements-dev.txt

# 全部测试（约 8 秒）
.venv/bin/python -m pytest tests -q

# 单个断电场景（示例：解锁到第 1 个文件后强杀）

.venv/bin/python -m cli.main recover /tmp/测试保险箱

# q120 次随机断电压力（约 25 秒）
.venv/bin/python scripts/stress_crash.py --rounds 60

# 性能（1 万文件 / 10 GB，约 3 分钟）
.venv/bin/python scripts/bench.py --files 10000 --file-size 1000000
```
